# ADR-001: Stack and Storage

**Status:** Accepted
**Date:** 2026-10-10
**Feature:** tessera-v1
**Author:** 10x-Team (Architect + Staff Engineer)

## Context

Tessera is a single-user, self-hosted app shipped as one Docker container. It needs a UI with fast keyboard-driven study sessions, a small JSON and form API, durable storage that is trivial to back up, and a single schema definition shared by the importer, API, and UI. Operator effort must stay near zero: no database server, no queue, no cache.

## Decision

1. **Framework:** SvelteKit 3.x with Svelte 5 (runes), Vite 8, TypeScript 6.x strict, `@sveltejs/adapter-node`. UI and API live in one codebase and one Node process.
2. **Storage:** SQLite through `better-sqlite3` 13, accessed via Drizzle ORM. Migrations are generated by `drizzle-kit`, committed under `drizzle/`, and applied on boot.
3. **Connection and pragmas:** one connection per process, created in `src/lib/server/db/client.ts`. On open: `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=NORMAL`.
4. **Validation:** Zod 4 defines the deck format once. `z.toJSONSchema` emits `static/schema/tessera-deck.v1.schema.json`, which `GET /api/schema` serves and CI diff-checks.
5. **Backup:** `VACUUM INTO` a temp file inside `DATA_DIR`, streamed to the caller and then removed. Pre-migration backups use the same method.
6. **Isolation of the driver:** all SQL goes through repositories in `src/lib/server/repos/`. No route or other module touches the connection directly. Swapping drivers later is a local change.
7. **Versions** are pinned exactly (`save-exact`) and verified again at scaffold time.

## Alternatives Considered

| Alternative | Pros | Cons | Why Not |
|---|---|---|---|
| `node:sqlite` (built in) | No native dependency, Drizzle has a driver | Node docs label it a release candidate. A third-party report says Node 24.15.0 (the version on the dev machine) truncates TEXT at embedded NUL characters. | Stability and a known data bug on the exact runtime. Revisit when it is stable. The repository layer keeps the switch cheap. |
| React SPA + Hono API + SQLite | Large contributor pool | Two build targets, more boilerplate, shared schema needs a workspace | More moving parts for one maintainer, no feature gain. |
| Python FastAPI + HTMX + SQLite | `py-fsrs`, Pydantic, easy to hack | Keyboard-driven study UI needs a lot of custom JS anyway. Two languages if a rich UI is needed. | Weaker fit for the interaction model. Schema sharing is lost. |
| Postgres | Concurrent writers, richer SQL | Second container, backup and upgrade burden | Single user, one writer. SQLite is sufficient and simpler. |
| Prisma instead of Drizzle | Mature tooling | Heavier engine binary, slower cold start, awkward with SQLite pragmas | Drizzle is lighter and SQL-shaped. |

## Consequences

### Positive

- One process, one volume, one file to back up. `docker compose up` is the whole install.
- A single Zod definition drives validation, TypeScript types, the published JSON Schema, and the Claude skill.
- Prebuilt SQLite binaries mean the image needs no compiler (see ADR-004).

### Negative

- SvelteKit 3.x is a new major line. Documentation and ecosystem examples may lag. Drizzle is pre-1.0, so API churn is possible.
- `better-sqlite3` is synchronous and blocks the event loop while a query runs. Acceptable for one user, and queries are sub-millisecond. A 5,000-card import is a single transaction measured in tens of milliseconds, to be confirmed by a benchmark in M1.
- TypeScript is held at 6.x until Kit widens its peer range.

### Risks

| Risk | Mitigation |
|---|---|
| Kit 3.x breaking change or bug blocks scaffolding | Scaffold in M1 day one. Fall back to the last Kit 2.x release if blocked and record it in a superseding ADR. |
| Drizzle API drift | Exact pin. Repositories confine the surface. |
| WAL files left behind in backups | Backup always uses `VACUUM INTO`, never a raw file copy while running. Docs say to stop the container before copying files by hand. |

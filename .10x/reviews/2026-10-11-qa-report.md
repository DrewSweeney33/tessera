# QA Report: Tessera Milestone 1 (interim verification)

**Date:** 2026-10-11
**Phase:** 5 Verification, interim. The plan calls for full verification at the M2 and M5 exits. This pass covers the Milestone 1 slice as built: import, study, UI, container files.
**Feature slug:** `tessera-v1`
**Commit verified:** `bb53e77` on `main`
**Environment:** Windows 11, Node 24.15.0, Chrome (Playwright `channel: chrome`), production build. No Docker, no GitHub remote.

## Verdict

**The M1 slice is sound and safe to build M2 on.** Two defects were found and fixed during this pass. Nothing blocking remains. It is **not a release**: the container image has never been built and CI has never run, so those two paths are unverified. Details and conditions are at the end.

## Defects found

| ID | Severity | Finding | Status |
|---|---|---|---|
| Q-01 | Medium | The study screen had no level-one heading while a card, the loading state, or an error was showing. Screen reader users navigating by headings found nothing. Found by axe (`page-has-heading-one`). | **Fixed.** A visually hidden `h1` is rendered in every state except the done screen, which has its own. |
| Q-02 | Low | A request body over the limit sent with chunked transfer encoding (no `Content-Length`) returned **500** and logged an "unhandled error" instead of **413**. The review route also counted characters, not bytes. | **Fixed.** `readBodyText` enforces the byte cap itself, treats the adapter's size error as 413, and stops reading at the limit. 10 unit tests plus the probe. |

Two earlier findings from the UI work were also fixed before this pass and are recorded in the SDE log: the dark theme flashing light on load, and JSON syntax errors with no line number.

Test-suite defects found in my own new tests along the way (not product bugs): a probe that expected only 415 where SvelteKit's CSRF check answers 403 first (both layers are now tested separately), tests that pressed keys before the client-rendered page loaded, a deck shared between tests that each graded its cards, and a synthetic key event dispatched on `window`.

## Test coverage

Line coverage of `src/lib` is **92.1 percent**, branches **85.3 percent**, functions 92.2 percent (v8, unit plus integration). Most server and core areas are 94 to 100 percent. The lowest are `server/app.ts` (86 percent, start-up error branches) and `server/config.ts` (88 percent, the invalid-environment branches). The three files at 0 percent (`ui/api.ts`, `ui/clipboard.ts`, `ui/theme.ts`) are browser-only code that the tool cannot see; they are exercised by the Playwright specs (import, clipboard, theme persistence, blocked storage). `.svelte` components are not measured; they are covered by the browser tests. Coverage is a signal, not a goal, so the more useful evidence is the next section.

### Do the tests catch real bugs? (mutation check)

I introduced 15 deliberate bugs one at a time and ran the whole suite each time. **14 were caught**, each by the test that should catch it.

| Deliberate bug | Caught by |
|---|---|
| Replayed review ids not recognised | `submit.test.ts` |
| Stale reviews accepted | `study.test.ts` (API) |
| Leech threshold off by one | `submit.test.ts` |
| Unchanged cards treated as updated on re-import | `plan.test.ts` |
| Buried cloze siblings shown again | `submit.test.ts` |
| Daily new card limit ignored | `queue.test.ts` |
| Daily review limit ignored | `queue.test.ts` |
| Content type guard lets everything through | `http-helpers.test.ts` |
| Body size cap not enforced | `body.test.ts` |
| Wrong `nosniff` header | `hooks.test.ts` |
| Any request id trusted | `hooks.test.ts` |
| Card limit raised from 5,000 | `deck.test.ts` |
| Unknown `dry_run` values accepted | `api.test.ts` |
| Id pattern loosened | `deck.test.ts` |
| **CSP `script-src` loosened to allow inline scripts** | **Nothing in `verify`. Survived.** |

The survivor is a real gap: the CSP lives in `vite.config.ts` and only the built server shows it. The security probe checks it, but the probe was not in CI. **Fixed by adding the probe (and the durability check) to the CI workflow.** A separate earlier negative control (disabling DOMPurify) found and closed a gap in the XSS tests.

## Release readiness

**M1 exit gate: ready, with three conditions.**

1. The owner confirms the gate.
2. The first CI run on GitHub passes, including the Docker jobs and the new e2e, probe, and durability steps. Until then R-2 stands.
3. The security items marked for early M2 in the security review (host check, token design) are scheduled first.

Not ready for a `v0.1.0` tag, and it should not be: that gate belongs to M2.

# QA Report: Tessera 0.1.1 (release candidate 0.1.1-rc.1)

**Date:** 2026-10-12
**Phase:** 5 Verification for a follow-up release. The first report that includes a live-image harness run, as ADR-012 requires of every release.
**Feature slug:** `tessera-v1`
**Candidate:** `v0.1.1-rc.1`, commit `5c20def`, image `ghcr.io/drewsweeney33/tessera:0.1.1-rc.1` (digest `sha256:55f60979b455…`), published as a pre-release. `latest` and `0.1` still point at 0.1.0.
**Environments:** Windows 11 with Node 24.15.0 (unit, integration, Chromium, WebKit, probes); GitHub CI on Ubuntu (Chromium, Firefox, WebKit, both container architectures, image scan); the homelab Docker host (CT123, a Debian 13 unprivileged LXC with nested Docker on Proxmox) for the live-image harness.

## Verdict

**Ready for the owner's decision to release 0.1.1.** No open defect. Every defect found during this cycle is fixed and has a test that failed before the fix. The real-host run of the candidate image is clean: 63 passed, 0 failed, 1 skipped (a check that cannot apply to a remote server, named below). Nothing in this report is a guess about the real host: each claim below was run on it.

## Live-image harness run, on the real host

Five runs, in order, and what each taught:

| Run | Image | Result | Meaning |
|---|---|---|---|
| 1 | published 0.1.0 | stopped at the start | `/opt` is root-owned: harness defect H-1 (fixed). It stopped safely and tore down. |
| 2 | published 0.1.0 | 43 passed, 11 failed | The 0.1.0 image really had B-1 and the generic 500 on a full disk, and my crash step was wrong (H-2). The test instance ran the very image the live one runs (same digest). |
| 3 | built on the host from `HEAD` | build timed out | Building on this host hung in `npm prune` (a slow route to the npm registry from that container, cause not found). H-4. |
| 4 | candidate `0.1.1-rc.1` | 61 passed, 1 failed | The one failure was my kill matching on the wrong process name (H-3), proven with a diagnostic on a throwaway instance. |
| 5 | candidate `0.1.1-rc.1`, 5 minute soak | **63 passed, 0 failed, 1 skipped** | Clean. |

What run 5 shows, on the real host:

- **Hardening as Docker applies it:** non-root user (uid 1000), read-only root filesystem (a write to `/` is refused), all capabilities dropped, `no-new-privileges`, 512 MB memory limit, restart policy `unless-stopped`, log rotation, and only the test port published on the host address.
- **Application tests over the network:** smoke passes, the security probe passes 214 checks (plus the one named skip), and the benchmark passes (slowest import 2.16 s against a 10 s budget; study next 24 ms median, review 21 ms median).
- **Backup and restore with the guide's own commands:** the documented backup works, its integrity check prints `ok`, the backup was copied out, restored into a fresh volume, and a second instance on the restored data showed the same decks and card counts. This is the 0.1.0 failure, now passing.
- **Crash and stop:** the server process was found and killed inside the container, Docker restarted the container itself and it was healthy again in about 8 seconds, and the saved grade survived. An explicit `docker kill` leaves it stopped, as Docker defines it, and starting it again keeps the grade. A graceful stop exits with code 0, quickly, logs `shutting down`, and the grade survives it too.
- **Full disk, on an 8 MB memory-backed volume:** imports fail with HTTP 507 and a message that says the disk is full. The container does not crash or restart, reads keep working, imports work again once space is freed, and the integrity check is `ok`.
- **Soak, 5 minutes, four workers:** 15,227 successful requests, no unexpected statuses, no error log lines, and memory flat after warm-up at 75 to 82 MiB (53 MiB at the first sample).
- **Teardown:** the test folder, containers, and volumes were removed, the live instance was untouched, and a read-only check afterwards confirmed it.

**Skipped, by name:** "the server process is still running", which asks about a local child process and cannot apply to a remote server.

## Release readiness

**Ready for the final 0.1.1 on the owner's approval.** Steps, once approved: rename the changelog section to `0.1.1`, set `package.json` to `0.1.1`, push, wait for CI, tag `v0.1.1`, and watch the release workflow. Then upgrade CT123 by changing the image tag in its compose file and running `docker compose pull` and `docker compose up -d`. The final image is built by the same workflow from the same source as the candidate, but it is a separate build: the harness should be run once more against the final tag, which takes about 7 minutes.

# DBA Decisions: tessera-v1

**Phase:** 4 Implementation (running log)
**Source files:** `src/lib/server/db/schema.ts`, `drizzle/`

## Schema (migration 0000_init, 2026-10-10)

Six tables, built to the architect's section 5 including its deltas.

| Table | Purpose | Notes |
|---|---|---|
| `decks` | Deck metadata | Text slug primary key. `target_retention`, `new_per_day`, `exam_date` are nullable per-deck overrides. |
| `cards` | Authored cards | Integer `pk`, unique `(deck_id, key)`. Authored fields live in a JSON `content` column validated by `core/schema`. `position` orders new cards. |
| `card_state` | One row per schedulable review item | Primary key `(card_pk, ordinal)`. FSRS fields, `leech`, `buried_until`, `archived`. |
| `review_log` | Append-only history | Client UUID primary key (idempotent submit). Pre-review snapshot as columns. `result` JSON holds the post-review state for replay. |
| `settings` | User settings | Key and JSON-encoded value, keys in camelCase (`targetRetention`, `newPerDay`, `reviewsPerDay`, `rolloverHour`, `leechThreshold`, `interleave`). Seeded at boot with `insert or ignore`. |
| `import_history` | One row per committed import | Counts of new, updated, unchanged, archived cards. |

## Constraints

- Foreign keys are on. Cards reference decks without cascade. `card_state` and `review_log` cascade from cards (cards are archived, never deleted, in v1).
- CHECK constraints: card type, phase 0 to 3, grade 1 to 4, log mode `review` or `cram`.
- Booleans are 0 or 1 integers with default 0. JSON columns default to `'[]'` where they hold lists.

## Indexes

| Index | Serves |
|---|---|
| `cards_deck_key_unique (deck_id, key)` | Import reconciliation lookup and identity |
| `cards_deck_position_idx (deck_id, position)` | New-card ordering |
| `card_state_due_idx (due) where archived = 0` | Partial index for the due queue, excludes archived items |
| `card_state_phase_idx (phase)` | Counts by state for stats |
| `review_log_card_idx (card_pk, reviewed_at)` | Per-card history, leech reports, recent wrong answers |
| `review_log_time_idx (reviewed_at)` | Daily counts, heatmap, streaks |
| `review_log_mode_time_idx (mode, reviewed_at)` | Retention and counters that exclude cram |

The primary key of `card_state` already covers lookups by `card_pk`, so no separate index was added (the architect's list named one).

## Migration and backup policy

- Migrations are generated by `drizzle-kit generate`, committed under `drizzle/`, and applied at boot.
- Before applying pending migrations to a database that already has migration history, a snapshot is written with `VACUUM INTO` to `<dataDir>/backups/pre-migrate-<timestamp>.db`. A failure message names the backup file.
- Backups are not pruned in v1. They are small, and the docs should say they can be deleted once an upgrade is confirmed good.
- Pragmas on open: WAL, foreign keys on, busy timeout 5000 ms, synchronous NORMAL.
- Never copy `tessera.db` while the app is running. Use the backup endpoint (M3-07) or stop the container.

## Open items

- Query plans for the queue and stats queries are checked when those queries exist (M1-11 and M4-05), using `EXPLAIN QUERY PLAN`.
- A future migration that renames or drops columns must use the table-rebuild pattern because SQLite's `ALTER TABLE` is limited. Drizzle generates it, but it must be reviewed.

# Tessera v1 Design Spec

**Date:** 2026-10-10
**Status:** Approved by user on 2026-10-10
**Feature slug:** `tessera-v1`
**License:** AGPL-3.0

## 1. Summary

Tessera is an open source, self-hosted flashcard app for learning things quickly. Its primary function is accepting study decks generated by Claude through a documented, validated import format, and then scheduling reviews with a modern spaced repetition algorithm (FSRS). It ships as a single Docker container with SQLite storage.

The differentiator against existing apps (Anki, Brainy, Quizlet-style tools) is the **Claude round trip**: Claude writes a deck in a strict format, Tessera imports it, Tessera finds the cards and tags the learner struggles with, exports a weak-spot report, and Claude returns a revised deck that merges in without losing review history.

## 2. Goals and non-goals

### Goals

- Claude-generated decks import in one step (paste, file drop, or API call) with errors that Claude can fix when pasted back.
- Scheduling quality comparable to current Anki (FSRS), including short-term learning steps so new material sticks within a session.
- Four card types: basic, cloze, typed answer, multiple choice.
- Leech and weak-spot detection that feeds back into Claude.
- Cram mode for exam preparation that does not disturb the long-term schedule.
- Useful stats: retention, forecast, streak, weak tags.
- One `docker compose up` to run. One file to back up.

### Non-goals for v1

- User accounts, login, multi-user, sharing.
- Image or media uploads (cards are text, code, tables, and Mermaid diagrams).
- Auto-generated multiple choice distractors (deferred to v1.1).
- Native mobile apps and cross-device sync services (the web UI is responsive and installable as a PWA).
- An MCP server (deferred).
- Built-in LLM calls. Tessera never calls a model. Claude is an external author.

## 3. Decisions made during brainstorming

| Decision | Choice | Reason |
|---|---|---|
| Users | Single user, no login | Simplest container. Access control left to reverse proxy or VPN. |
| Scheduler | FSRS via `ts-fsrs` | Reference TypeScript implementation, strong retention per review. |
| Smart features | FSRS, leeches and weak spots, typed and cloze cards, cram mode and stats | All four selected by the user. |
| Import | JSON canonical plus Markdown authoring format, paste or upload or REST | Both formats selected by the user. |
| Stack | SvelteKit (adapter-node), TypeScript, SQLite | One codebase, shared Zod schema, small image. |
| Card content | Markdown, code blocks, Mermaid | Claude writes all of it as text, decks stay one portable file. |
| License | AGPL-3.0 | Protects a self-hosted app from closed hosted forks. |

## 4. Architecture

One Docker container. SvelteKit with `adapter-node` serves the UI and `/api` routes. SQLite (`better-sqlite3` with Drizzle ORM) lives at `/data/tessera.db` in a mounted volume. Migrations run on boot. The runtime is Node 24 LTS.

### 4.1 Units

| Unit | Responsibility | Depends on |
|---|---|---|
| `schema` | Zod definition of the deck format. Emits a JSON Schema file. Single source of truth. | none |
| `import` | JSON parser and Markdown parser, both producing one normalized deck. Validate, preview a diff, commit in one transaction. | `schema` |
| `scheduler` | Pure wrapper around `ts-fsrs`. Maps grades to state changes. Cram mode lives outside it and never writes FSRS state. | ts-fsrs |
| `study` | Builds the study queue and prepares each card type for rendering and grading. | `scheduler` |
| `stats` | Retention, review forecast, streaks, per-tag retention, card-state counts. | review log |
| `export` | Deck export in both formats, full database backup, weak-spot report for Claude. | `schema` |

Each unit exposes a small typed interface and is testable without the others.

### 4.2 Configuration (environment variables)

| Variable | Default | Purpose |
|---|---|---|
| `PORT` | `3000` | HTTP port. |
| `DATA_DIR` | `/data` | SQLite database and backups. |
| `TESSERA_API_TOKEN` | unset | If set, external `/api/*` write calls require `Authorization: Bearer <token>`. |
| `TZ` | `UTC` | Time zone used for day rollover and streaks. |

User-facing settings (rollover hour, daily limits, target retention, leech threshold, interleave) live in the `settings` table and are edited in the UI.

## 5. Data model

SQLite tables. All timestamps are UTC ISO 8601 text.

| Table | Key columns |
|---|---|
| `decks` | `id` (slug, pk), `title`, `description`, `tags` (json), `target_retention` (nullable override), `new_per_day` (nullable override), `exam_date` (nullable), `archived`, `created_at`, `updated_at` |
| `cards` | `pk` (integer), `deck_id`, `key` (slug, unique within deck), `type` (`basic`, `cloze`, `typed`, `choice`), `content` (json, type-specific), `tags` (json), `source`, `content_hash`, `archived`, `suspended`, `created_at`, `updated_at` |
| `card_state` | `card_pk`, `ordinal` (0 for non-cloze, the cloze number otherwise), FSRS fields (`due`, `stability`, `difficulty`, `elapsed_days`, `scheduled_days`, `learning_steps`, `reps`, `lapses`, `state`, `last_review`), `leech` (bool), `buried_until`. Primary key is `(card_pk, ordinal)`. One row per schedulable review item. |
| `review_log` | `id` (client-supplied UUID, pk, makes submission idempotent), `card_pk`, `ordinal`, `mode` (`review` or `cram`), `grade` (1 to 4), pre-review state snapshot, `scheduled_days`, `duration_ms`, `typed_answer` (nullable), `reviewed_at`. Append-only. |
| `settings` | `key`, `value` |
| `import_history` | `id`, `deck_id`, `format`, `filename`, counts (new, updated, unchanged, archived), `created_at` |

Notes:

- A cloze card with `c1` and `c2` produces two `card_state` rows. A basic, typed, or choice card produces one.
- `review_log` keeps the full pre-review state so the FSRS parameter optimizer can run on it later.
- Indexes: `card_state(due)`, `card_state(state)`, `cards(deck_id, key)` unique, `review_log(card_pk, reviewed_at)`.

## 6. Deck format

JSON is canonical. The Markdown format converts to JSON during import, so there is one validator. Both formats carry a version marker (`tessera: 1`). Unknown fields are rejected.

### 6.1 JSON

```json
{
  "tessera": 1,
  "deck": { "id": "ccna-ospf", "title": "CCNA: OSPF", "description": "OSPF fundamentals", "tags": ["ccna"] },
  "cards": [
    { "id": "ospf-hello", "type": "basic", "front": "Default OSPF hello interval on broadcast networks?", "back": "10 seconds", "hint": "Dead is 4x this", "tags": ["timers"], "source": "Lesson 3" },
    { "id": "ospf-dr", "type": "cloze", "text": "The {{c1::DR}} is elected by highest {{c2::priority}}.", "extra": "Ties break on router ID." },
    { "id": "ospf-show-nbr", "type": "typed", "front": "Command to list OSPF neighbors?", "answer": "show ip ospf neighbor", "accept": ["sh ip ospf nei"] },
    { "id": "ospf-lsa", "type": "choice", "front": "Which LSA type describes a network segment?", "choices": ["Type 1", "Type 2", "Type 3", "Type 5"], "correct": 1, "explanation": "The DR originates Type 2." }
  ]
}
```

Field rules:

- Deck `id` and card `id` match `^[a-z0-9][a-z0-9-]{0,63}$`. Card ids are unique within a deck.
- Card `id` is strongly recommended. If omitted, the id is a hash of the normalized front or text, which means editing that text creates a new card. The importer warns about this.
- `basic`: `front`, `back` required. `hint`, `tags`, `source` optional.
- `cloze`: `text` required with at least one `{{cN::answer}}` marker. `extra` optional.
- `typed`: `front`, `answer` required. `accept` optional list of alternate accepted answers.
- `choice`: `front`, `choices` (2 to 8 strings), `correct` (index) required. `explanation` optional.
- All text fields are Markdown. Code fences and `mermaid` fences are allowed.

### 6.2 Markdown

```markdown
---
tessera: 1
id: ccna-ospf
title: "CCNA: OSPF"
tags: [ccna]
---

## ospf-hello
Q: Default OSPF hello interval on broadcast networks?
A: 10 seconds
Hint: Dead is 4x this
Tags: timers
Source: Lesson 3

## ospf-dr
Cloze: The {{c1::DR}} is elected by highest {{c2::priority}}.

## ospf-show-nbr
Q: Command to list OSPF neighbors?
Answer: show ip ospf neighbor
Accept: sh ip ospf nei

## ospf-lsa
Q: Which LSA type describes a network segment?
Choices:
- Type 1
- [x] Type 2
- Type 3
- Type 5
Explanation: The DR originates Type 2.
```

Parsing rules:

- A `## <id>` heading starts a card. Frontmatter holds the deck fields.
- A field continues until the next field label or heading. Fenced code blocks are opaque, so labels inside a fence are never parsed.
- Type is inferred: `Cloze:` is cloze. `Q:` with `Choices:` is choice. `Q:` with `Answer:` is typed. `Q:` with `A:` is basic. An optional `Type:` line overrides inference.
- `Tags:` and `Accept:` are comma separated.

## 7. Import behavior

Entry points:

- UI: paste into a text box or drop a file (`.json`, `.md`).
- API: `POST /api/import` with `Content-Type: application/json` or `text/markdown`. Query flags: `dry_run=true`, `archive_missing=true`.

Flow: parse, validate, build a diff against existing cards, show a preview (new, updated, unchanged counts), commit.

Rules:

1. **Atomic.** The whole import is one SQLite transaction.
2. **Idempotent.** Cards match on `(deck_id, key)`. If `content_hash` is unchanged, nothing is written. If it changed, content is updated and the review schedule is kept.
3. **Cloze changes.** New cloze numbers create new `card_state` rows. Removed numbers archive their rows.
4. **No silent deletion.** Cards absent from a re-import are left alone. The `archive_missing` flag archives them instead. Nothing is ever hard-deleted by import.
5. **Limits.** 5 MB and 5,000 cards per import.
6. **Errors Claude can fix.** Each error has a path (`cards[12].back`), a plain sentence, and where possible the allowed values. The UI has a "Copy errors for Claude" button that builds a ready-to-paste fix request containing the errors and a pointer to the schema.

Claude-facing assets:

- `GET /api/schema` returns the JSON Schema.
- The repo ships `claude-skill/tessera-deck/SKILL.md`: the format, plus card-writing guidance (one fact per card, cloze for lists and sequences, stable ids, prefer typed cards for commands and terms).

## 8. Study experience

- Home lists decks with due and new counts. A session shows the front, Space reveals, keys 1 to 4 grade (Again, Hard, Good, Easy) and each button shows its next interval.
- Keyboard-first. Responsive layout. Installable PWA. Light and dark themes.

| Type | Interaction | Grading |
|---|---|---|
| Basic | Reveal, then self-grade | User picks 1 to 4 |
| Cloze | Each cloze number is its own review item | User picks 1 to 4 |
| Typed | Type the answer. Case and extra whitespace are ignored, `accept` list is checked | Match suggests Good, mismatch suggests Again, user can override |
| Choice | Click an option | Correct is Good, wrong is Again |

## 9. Scheduling and smart learning

- **FSRS** through `ts-fsrs` with default parameters. Target retention 0.90 (per-deck override). Short-term learning steps enabled so new cards repeat within the same session. Fuzz enabled.
- **Limits and rollover.** Defaults: 20 new cards per day, 200 reviews per day, 4am day rollover.
- **Queue order.** Learning cards, then reviews ordered by lowest predicted recall first, then new cards. Optional interleave setting mixes tags.
- **Burying.** Sibling cloze items of one card are buried until the next day after one is reviewed.
- **Review log.** Every grade is stored with the pre-review state so the FSRS optimizer can personalize parameters later.

### 9.1 Leeches and weak spots

- A review item reaching 8 lapses (configurable) is flagged `leech`. It is not auto-suspended.
- The leech list offers: copy a rewrite request for Claude, suspend, or reset the item.
- The dashboard ranks tags by retention and lapse rate.
- **Weak-spot report** (`GET /api/report/weak-spots`, also a UI button): Markdown and JSON containing leech cards with their full content, lapse counts, and typed wrong answers, plus the weakest tags and the schema pointer. Written so it can be pasted to Claude with the instruction "rewrite these cards, return a revised deck".

### 9.2 Cram mode

Per deck, with an optional exam date. Scope is all cards, a tag, or weakest first. The session is shuffled. Grades are logged with `mode = cram` and never change FSRS state.

### 9.3 Stats

Today's reviews, true retention, a 30-day review forecast, streak and heatmap, per-tag retention, and card-state counts (new, learning, review, leech).

## 10. HTTP API

| Method and path | Purpose |
|---|---|
| `GET /healthz` | Liveness and database check. |
| `GET /api/schema` | JSON Schema for the deck format. |
| `POST /api/import` | Import a deck (see section 7). |
| `GET /api/decks` | List decks with counts. |
| `GET /api/decks/:id/export?format=json\|md` | Export a deck. |
| `GET /api/report/weak-spots` | Weak-spot report for Claude. |
| `GET /api/backup` | Consistent database snapshot (`VACUUM INTO`). |

Write endpoints honor `TESSERA_API_TOKEN` when set. The UI uses SvelteKit form actions with the built-in CSRF origin check.

## 11. Security

- The container listens on all interfaces. Docs state that Tessera has no login and must sit behind a reverse proxy with authentication or a VPN.
- `TESSERA_API_TOKEN` protects the external API only. UI access control is the reverse proxy's job.
- Rendered Markdown is sanitized with no raw HTML. Mermaid runs with `securityLevel: strict`. A Content-Security-Policy header is set.
- All queries are parameterized through Drizzle. Zod rejects unknown fields. Import size and card-count limits apply.
- The container runs as a non-root user, writes only to `/data`, and contains no secrets.

## 12. Reliability

- Imports are atomic.
- The database is copied to `DATA_DIR/backups/` before any migration runs.
- A review writes card state and the log row in one transaction. The client-supplied UUID prevents double submission.
- A card that fails to render shows raw text with an error badge and does not break the session.

## 13. Testing

- **Unit (Vitest):** schema, both parsers, scheduler wrapper, queue builder, typed-answer matcher. Properties: JSON and Markdown forms of one deck import to identical results, and re-importing an unchanged deck writes nothing.
- **Scheduler conformance:** fixture review sequences produce the same states as the `ts-fsrs` reference.
- **Integration:** API against a temporary SQLite file, including atomic rollback on a bad import and migration backup.
- **End to end (Playwright):** import, study, grade, stats, leech, cram.
- **Golden fixtures:** realistic Claude-written decks, plus malformed ones with expected error messages.

## 14. Delivery

- GitHub Actions: lint, typecheck, unit and integration tests, e2e, Docker build, container smoke test against `/healthz`. Multi-arch images (amd64 and arm64) published to GHCR.
- The repo ships `Dockerfile`, `compose.yaml`, `LICENSE` (AGPL-3.0), `README.md`, docs, and the Claude skill.
- Docker is not installed on the primary development machine, so CI is the first place the image is built and smoke tested. The user can also verify on a homelab host.

## 16. Success criteria

- A deck produced by the Claude skill imports without manual edits on realistic fixtures, and malformed fixtures produce errors that identify the exact field.
- Importing a 500-card deck completes in under 2 seconds.
- Scheduler output matches the `ts-fsrs` reference on all conformance fixtures.
- A study session is fully operable by keyboard.
- Container image is under 250 MB and reaches a healthy state in under 10 seconds.
- Updating a deck and re-importing preserves all existing review history.

## 17. Risks

| Risk | Mitigation |
|---|---|
| `better-sqlite3` native build on arm64 or slim images | Use a Debian-based Node image with prebuilt binaries. Confirm in an ADR and the CI matrix. |
| Mermaid bundle size slows the UI | Lazy-load Mermaid only for cards that contain a diagram. |
| `ts-fsrs` API changes between versions | Pin the version. Isolate behind the `scheduler` unit with conformance tests. |
| LLM-written decks contain bad cards | Validation, preview step, leech detection, and the weak-spot round trip. |
| Exposure without auth | Explicit docs, optional API token, non-root container. |
| Competition from Brainy and Anki | Differentiate on the Claude round trip and the strict import schema. |

## 18. Deferred

Auto-generated choice distractors (v1.1), image and media support, MCP server, accounts and multi-user, FSRS parameter optimizer UI, sync and native apps.

## 19. Amendments from Phase 2 (2026-10-10)

These refine the approved spec. Details and reasoning are in ADRs 001 to 005 and `.10x/decisions/architect/tessera-v1.md`.

1. **Layout (section 14):** source is split into `src/lib/core` (pure, isomorphic), `src/lib/server`, and `src/lib/ui`, with lint-enforced import rules.
2. **Image size (sections 14 and 16):** the target is a compressed manifest size under 150 MB per architecture, measured in CI. Base image is `node:24-trixie-slim` (about 79 MB compressed).
3. **API token (sections 4.2 and 10):** when `TESSERA_API_TOKEN` is set, every `/api/*` route except `/healthz` and `/api/schema` requires the token, not only write routes. Added optional `TESSERA_ALLOWED_HOSTS` and the required `ORIGIN` setting behind a proxy.
4. **Compose sample (section 14):** publishes on loopback (`127.0.0.1:3000:3000`) by default, with a read-only root filesystem, dropped capabilities, and a named data volume.
5. **Data model (section 5):** `cards.position` added, `card_state.archived` added, review snapshot stored as columns, default settings seeded at first boot.
6. **Rendering (sections 8 and 11):** the app runs with `ssr = false`. Markdown is rendered client-side only through one sanitizing component.
7. **Frontmatter parsing (section 6.2):** uses the `yaml` package with the core schema. `gray-matter` is rejected because it can execute JavaScript frontmatter.
8. **Review submission (section 9):** server-authoritative queue, one item at a time, with an idempotency key and a stale-review check.
9. **Retype of a card (section 7):** changing a card's type on re-import resets that card's progress and is flagged in the preview.

## 20. Amendments from Phase 3 (2026-10-10)

Milestone changes from `.10x/decisions/engineering-manager/tessera-v1.md`:

1. **Claude skill moves from M3 to M2.** The checkpoint needs the owner to study a Claude-generated deck, so the skill and three golden decks ship with M2. M3 extends the skill with the weak-spot round trip.
2. **Mermaid and Shiki land in M2**, together with the CSP verification.
3. **CSP, request ids, and content-type enforcement land in M1.** API token and allowed-hosts enforcement land in M2.
4. **First release is `v0.1.0` at the end of M2**, deployed to the homelab to start the study checkpoint. `v1.0.0` follows M5.
5. **Settings UI and the interleave option land in M3.** M1 and M2 run on seeded defaults.
6. **Charts are hand-rolled SVG**, no chart library.
7. **PWA scope** is an installable app shell with no offline study, because the study queue is server-authoritative.
8. **Plan size:** 67 tasks across five milestones, about 224 human-equivalent hours.

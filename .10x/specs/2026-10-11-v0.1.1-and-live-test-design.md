# Design: Tessera 0.1.1 and the live-image test harness

**Date:** 2026-10-11
**Feature slug:** `tessera-v1` (a follow-up release inside the same product)
**Status:** Draft for the owner's review. Nothing in this document has been implemented.
**Decided by the owner on 2026-10-11:** do 0.1.1 first, then M3. The live test harness (B-2) runs a test instance on the homelab LXC and the scripts from the owner's PC.

## Why

Tessera 0.1.0 is released and runs on the homelab (CT123, `https://tessera.sweentech.com`). The first real deploy found one defect (B-1) and showed gaps that CI cannot see: CI runs the image on a CI runner, not on a real Docker host behind a real proxy. Several risks in the M2 QA report can only be closed on a real host (R-2 compose on a real host, R-7 disk full, R-8 long soak). The goal of this work is to fix what the deploy found and to make real-host testing a command instead of a manual evening.

## Design

### B-1: create `/data/backups` at startup

**Problem.** `src/lib/server/db/migrate.ts` creates the folder only when it takes a backup before an upgrade. On a fresh install that never happens, so the manual backup command in `docs/operations.md` fails with `SQLITE_CANTOPEN` and its integrity check with "directory does not exist".

**Change.** Where the server prepares its data folder (the place that already refuses to start when the folder is not writable), also create `<dataDir>/backups` with `mkdir -p`. The migration code keeps its own `mkdir` as a second safety. No schema or API change.

**Edge cases.** A data folder that is not writable already stops the server with the `chown` hint. A `backups` path that exists as a file, not a folder, stops the server with a clear message (today it would fail later and confusingly). Creating the folder must not change the owner or mode of anything that exists.

**Tests (written first).**
1. Start the server on an empty data folder: `backups/` exists afterwards, and the server is healthy.
2. Run the exact backup command and the exact integrity-check command from `docs/operations.md` (extracted from the marked blocks, not retyped) against a fresh data folder and expect success and `ok`. This is the test that would have caught B-1.
3. `backups` exists as a file: a clear start-up error.
4. A mutation check: remove the new `mkdir`, and test 1 and 2 must fail.

### S-11: log rotation in `compose.yaml`

Add `logging: { driver: json-file, options: { max-size: '10m', max-file: '3' } }` to the service, and one sentence in `docs/operations.md`. The container policy test gets a case that checks the setting. The server logs one line per request, so an endless log is the only way a normal install could slowly fill a small disk.

### D-1: the published image in the deploy guide

A section in `docs/deploy.md` that shows the same hardened compose file with `image: ghcr.io/drewsweeney33/tessera:<version>` and no `build:`, the update steps (`docker compose pull`, `docker compose up -d`), and a warning to pin an exact version. The docs test checks that the example parses and keeps the hardening keys (read-only, dropped capabilities, no-new-privileges), so the example cannot drift from `compose.yaml`.

### F-1: favicon

Reuse the logo mark from the page header as `static/favicon.svg` and add `<link rel="icon" href="/favicon.svg" type="image/svg+xml">` to `src/app.html`. Browsers that find the link do not ask for `/favicon.ico`. Light and dark: the mark uses the theme colours, so one SVG with `prefers-color-scheme` inside it. The CSP already allows images from the same origin. A browser test checks the link and that the file is served with an image content type.

### B-2: the live-image test harness

**Goal.** One command runs the real published image on the real Docker host, exercises it, and removes everything it made.

**Where it runs.**

```
owner's PC  --ssh-->  CT123 (192.168.30.102)
   |                    /opt/tessera-test/  (compose project "tessera-test", port 3001, own volume)
   +--- HTTP ---------> http://192.168.30.102:3001
```

The harness script, `scripts/live-test.ts`, runs on the PC. It uses SSH (key login, no password prompt) for Docker commands on the LXC, and plain HTTP for the app tests, with the existing scripts (`smoke`, `security-probe`, `benchmark`) pointed at the test instance by `--base`. The live instance (`/opt/tessera`, port 3000) is never touched.

**Safety rules, enforced in the script and tested.**
1. It only ever works in a folder named `tessera-test` and a compose project of the same name, and writes a marker file there. It refuses to remove anything that lacks the marker.
2. It refuses a target port of 3000 (or the live instance's port, given in a flag), and refuses to run when the test project and the live project share a volume name.
3. `--dry-run` prints every command and does nothing.
4. Teardown (`down -v` and removing the folder) runs in a `finally` block, so a failed run does not leave a test instance behind.
5. Nothing secret is stored: the SSH target comes from an environment variable.

**Steps, each pass or fail with a reason.**

| # | Step | What it proves on a real host |
|---|---|---|
| 1 | Pull the image for the version in `package.json` and start the test project | The published image runs under the LXC's nested Docker |
| 2 | Health, then `docker inspect`: non-root user, read-only root filesystem, no capabilities, `no-new-privileges`, memory limit, restart policy | The hardening in `compose.yaml` actually applies on this host (R-2) |
| 3 | `smoke`, `security-probe` (live profile), `benchmark` from the PC | Behaviour and speed over the real network. The probe's log-leak checks read `docker compose logs` over SSH, since the server is remote |
| 4 | Backup, integrity check, copy out, restore into a fresh volume with the documented commands, compare card and review counts | The backup and restore guide works as written |
| 5 | `docker kill -s KILL` right after an acknowledged grade, restart, counts unchanged. `docker stop`, graceful shutdown logged | Durability and restart policy on the real host |
| 6 | Disk full: a second test project whose volume is a size-limited tmpfs (a few MB). Import until it is full | A full disk gives a clear error, no crash, no corruption, and the app recovers when space returns (R-7) |
| 7 | Optional `--soak <minutes>`: sustained mixed load, memory sampled with `docker stats` | Memory stays flat over time (R-8) |
| 8 | Teardown | Nothing left behind |

**The probe's live profile.** Today the probe, when given `--base`, still starts extra local servers for the token and host-rule checks and has no access to the server's log. The harness starts the test instance with the default host rules and no token (so the default-rules checks apply as written), runs the log-based checks against the logs it fetches, and runs the token and host-rule variants as separate test projects the harness starts for the purpose, so no check silently turns into a skip. Any check that cannot run in live mode is listed as SKIPPED with a reason, never as PASS.

**Out of scope for B-2.** Testing through NPM and the browser (the owner does that by hand once per release), and the multi-day soak (an owner task: leave the instance running).

## Failure modes and mitigations

| Failure | Mitigation |
|---|---|
| A bug in the harness touches the live instance | Rules 1 and 2 above, a dry run, and the live instance's compose project name is never in the allow list |
| SSH drops mid-run and leaves a test instance | Teardown also runs at the start of the next run (`down -v` on the marker folder) |
| Disk-full test fills the real disk | The size limit is on a tmpfs volume, not on the LXC's disk |
| The image under test is not the image in use | The harness prints and compares the image digest it runs against the digest of the live container |
| The harness makes the public repository depend on the owner's homelab | The target comes from an environment variable and the script is generic for any Docker host reachable over SSH. The docs describe it that way |

## Process

This is a medium task. ADR-012 will record the harness decision. Order of work: ADR and decision files, then B-1 (test first), S-11, D-1, F-1, then the harness, then a QA and security pass, then the release `0.1.1` after the owner's approval.
